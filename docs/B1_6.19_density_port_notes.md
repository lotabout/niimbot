# Niimbot B1 firmware 6.19 — density → coefficient port ledger

> Target device: Niimbot B1, **HW 6.01 / FW 6.19**.
> Upstream scheme: ThreeDaPrint/niimbot `B1_5.22_density_coeff.bin`
> (fw 5.22, md5 `023ff56326fe8c65f01b68f32ebdba99`).
> Paths follow this repository's layout (`firmware/`, `build/`, `repro/`, `src/`, `docs/`).
> Stock firmware is **not** distributed here (Niimbot copyright) — fetch it from
> <https://fw.niim.blue/stable/B1/>.
>
> This document records every basis and the verification state for "port the upstream 5.22
> Cortex-M0 code-cave scheme to 6.19 by address substitution".
> Result: `firmware/B1_6.19_density_coeff.bin` (md5 `43065da9717c4ba533c6669cc7a8e9b9`).

## 0. Summary

6.19 and 5.22 are **isomorphic**: both renderer entries, the soft-float multiply routine
and the config struct layout correspond item by item. The port is therefore address
substitution — the detour design did not have to be re-engineered. The produced image is
the 6.19 full-energy baseline plus 4 code injections.

**The upstream 5.22 cave encoder is anchored byte-for-byte**: using the same encoder as
this port (`enc_bl` / `build_cave_a` / `build_cave_b` in
`build/build_b1_619_density.py`) and swapping in the 5.22 addresses only, rebuilding from
stock `B1_5.22.bin` reproduces the upstream released image with **0 bytes difference**
(`repro/reproduce_522_density.py`). The only uncertainty left on the 6.19 side is
"were the addresses swapped correctly", and that has independent evidence (§2/§3).

## 1. Address map (5.22 → 6.19)

| Item | 5.22 | 6.19 | Delta | How it was established |
|---|---|---|---|---|
| base coefficient group (4 floats) | `0x01011dec` | `0x01011e60` | +0x74 | original values 74.4/60.0/60.8/120.0 identical |
| renderer A coefficients (6 floats) | `0x01016538` | `0x01016600` | +0xC8 | original values 20/50/30/150/100/90 identical |
| renderer B coefficients (5 floats) | `0x01016c84` | `0x01016d4c` | +0xC8 | original values 10/30/50/120/100 identical |
| **renderer A entry** | `0x01016124` | `0x010161ec` | +0xC8 | first 20 instructions **byte-identical** (incl. entry `push {r0-r7,lr}`) |
| **renderer B entry** | `0x01016844` | `0x0101690c` | +0xC8 | same, first 20 instructions byte-identical |
| **soft-float multiply routine** | `0x0102529a` | `0x01026156` | +0xEBC | first 48 bytes **byte-identical** |
| **density config byte** | `0x00020704` | `0x00020740` | +0x3C | see §3 |
| line-period table 64×u16 | `0x0102c2a4` | `0x0102d21c` | +0xF78 | all 64 values identical |

**Hook point** = entry + 2 (right after the entry `push`) — the same in 5.22 and 6.19:

| Hook | 6.19 address | Original bytes | Original instructions |
|---|---|---|---|
| hook124 | `0x010161ee` | `16 46 ff 36` | `mov r6,r2` / `adds r6,#0xff` |
| hook844 | `0x0101690e` | `14 46 06 46` | `mov r4,r2` / `mov r6,r0` |

Both entries use `push {r0-r7,lr}` (9 registers), so the detour stack offsets are exactly
those of 5.22: renderer A's input arg5 is at `[sp,#0x38]`; renderer B's arg6/arg7 are at
`[sp,#0x3c]` / `[sp,#0x40]`.

## 2. Evidence chain (three levels)

1. **Released-image anchoring (strongest)** — `repro/reproduce_522_density.py`: the same
   encoder plus the same rules applied to stock 5.22 reproduces the upstream density image
   byte-for-byte (0 differences). This anchors: 15 floats → 400, line-period
   `floor(old*1.5)`, both RFID bytes, the `bl` encoding, the detour `push`/`pop` and stack
   offsets, the replayed displaced instructions, the m-table bytes and the cave layout.
2. **Isomorphic disassembly** — the 6.19 counterparts match 5.22 instruction for
   instruction (table above), so the structure and register conventions are unchanged.
3. **Runtime reference confirmation** — each 6.19 address is confirmed through the code's
   own reference chain:
   - The config validator at `0x01010d88` range-checks `[r3,#4]` with `subs #1; cmp #5`
     and writes back a default of 3, `[r3,#5]` → 1..3 default 2, `[r3,#6]` → 1..5 default 1;
     `r3` is loaded from a literal pool entry = **`0x0002073c`**. The 5.22 function
     `0x01010d1a` has the same literal (`0x00020700`) at the same position and an
     instruction-identical body.
   - The SetDensity handler at `0x01022a78` validates the `45 04 00 06` header, clamps
     payload[4] to 1..5 and performs the `strb`; its `ldr r1,[pc,#0xd0]` literal measures
     **`0x0002073c`** (same position in 5.22 `0x01021db0` = `0x00020700`).
   - The reference counts of neighbouring variables in the 0x207xx block shift by +0x3C as
     well: `0x20600→0x2063c`, `0x20604→0x20640`, `0x20628→0x20664`, `0x206c0→0x206fc`,
     `0x20700→0x2073c`.
   ⇒ **density byte = `0x00020740`** (CFG+4).

## 3. Cave selection (zero-run scan on 6.19)

Rule: a run must be entirely zero bytes **and** hit by no `ldr` literal value and no
`b`/`bl`/`adr` target (scan over the whole image, 2-byte aligned linear decode; the
reference set contained 3993 targets). Only two runs in 6.19 are ≥48 bytes and completely
unreferenced:

| Zero run | Length | Use | Used |
|---|---|---|---|
| `0x0102cb62`–`0x0102cbb7` | 86 B | cave A (scale + m-table + literal pool), 4-byte aligned start `0x0102cb64` | 68 B (16 spare) |
| `0x0102c1ed`–`0x0102c21d` | 49 B | cave B (det124 + det844), start `0x0102c1ee` | 44 B (4 spare) |

Every other candidate run is referenced (e.g. the 157 B run `0x0102b6bd`–`0x0102b759`
contains 2 referenced addresses). **Do not** reuse those.

## 4. Injection points on 6.19

| Site (vaddr) | File off | Original | Patched | Meaning |
|---|---|---|---|---|
| `0x010161ee` | `0x61ee` | `16 46 ff 36` | `15 f0 fe ff` | `bl det124` (cave B) |
| `0x0101690e` | `0x690e` | `14 46 06 46` | `15 f0 77 fc` | `bl det844` (cave B+18) |
| `0x0102cb64` | `0x1cb64` | 68 B of zeros | cave A | `scale` + m-table + pool (`0x00020740` / `0x0102cb88` / `0x01026157`) |
| `0x0102c1ee` | `0x1c1ee` | 44 B of zeros | cave B | `det124` / `det844` |

Together with the baseline (15 floats + 64 line-period entries + 2 RFID bytes = 192 bytes
covered), the image differs from stock 6.19 in **270 bytes, 31 difference runs, 0 bytes
outside the allowed regions**.

## 5. Reproduce and verify

```bash
# read-only verification (10 checks, incl. capstone disassembly read-back)
python3 repro/verify_b1_619_density.py --src <stock B1_6.19.bin>

# rebuild from stock 6.19
python3 build/build_b1_619_density.py --src <stock B1_6.19.bin> --out rebuilt.bin

# root evidence: reproduce the upstream 5.22 image with the same encoder (expect 0 bytes diff)
python3 repro/reproduce_522_density.py            # needs a stock B1_5.22.bin
```

The verifier covers: source md5/size, candidate size, the 15 coefficients, the 64
line-period entries, both RFID bytes, the hook `bl` literals and decoded targets, the cave
bytes against a rebuild, capstone read-back (`bl` targets / stack offsets / displaced
instructions), the difference-region constraint, and md5/sha256.

## 6. Open items (do not present as proven)

1. **U1 energy calibration** — the m-table and `400.0` are values upstream calibrated on
   **5.22** (200 faint / 250 not solid / 325 close / 370 nearly / 400 solid / 500 solid /
   700 still solid). Whether the 6.19 print head batch, supply and paper match is unknown;
   whether D5 is "solid without over-burning" can only be settled on hardware (A/B).
2. **U2 timing** — line-period ×1.5 was verified safe on upstream 5.22 hardware (×2 drops
   lines); it is unverified on 6.19.
3. **U3 dual-colour paper** — the baseline also raises renderer A's six coefficients to 400,
   so the red grade of red/black dual-layer paper will very likely be lost (dual-colour =
   monochrome head + dual-layer thermal paper, graded by the energy window). To keep it,
   skip renderer A's six coefficients (the upstream density scheme does not handle this
   either).
4. **This build has never been flashed to or printed on any device** — every conclusion
   above comes from static analysis and byte-exact reproduction of released images.
5. The `.s`/`.ld` files are equivalent assembly sources and were **not** assembled with
   arm-none-eabi on this machine (no such toolchain available). The authoritative bytes are
   the output of `build/build_b1_619_density.py`, whose encoder is anchored by the released
   image reproduction in §2.

## 7. Flash and revert

```bash
npx --yes @mmote/niimblue-node flash -t serial -a /dev/ttyACM0 -n 6.19 \
  -f firmware/B1_6.19_density_coeff.bin
# the printer powers itself off afterwards — press the power button
```

- Revert: stock 6.19 image (fetch it yourself), md5 `fd9efd1441b5f05ca46c310b8d162dc1`;
  same major version, so cross-flashing is safe.
- **Never** flash any 5.22 image onto this device (cross-major flashing bricks it).
- Testing requires **third-party / untagged thermal paper**: genuine stock paper carries an
  RFID tag and always prints dark regardless of firmware, so it cannot show any density
  difference. Take a baseline print on third-party paper before flashing.
