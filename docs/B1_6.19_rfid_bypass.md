# Niimbot B1 firmware 6.19 — RFID read-failure bypass (`WriteRfidFail`, error 0x14)

> Symptom: niimblue aborts every print on untagged / third-party paper with
> `Print error 20: WriteRfidFail`, on **stock** 6.19 as well as on the patched images.
> Reproduced on hardware with stock 6.19 (md5 `fd9efd1441b5f05ca46c310b8d162dc1`).
> Upstream 5.22 never shows this: 5.22 has no error-0x14 path at all.

## 1. Where the error comes from

| Item | 6.19 | Note |
|---|---|---|
| status word | `[0x20614 + 0x14]` = `0x20628` | one bit per printer error |
| status → error code | `0x10108e2` | bit0→1 … bit14→0xF, **bit19→0x14**; 5.22's function stops at bit14 |
| `0xDB` sender | `0x101d4ee` | called from the main loop (`0x1010610`) and the PrintStart (`0x101e010`) / PageStart (`0x101e1f6`) handlers via `0x101d6f0` |
| RFID module | `0x1024c00`–`0x1025b80` | ~3.7 KB **not present in 5.22**; strings `LABEL RFID OK/ERR`, `uuid:` |
| RFID state struct | `0x205b8` | `+2` request bits (bit0 read, bit1/bit6 write-back, bit4 reader enabled), `+8` "first failure seen", `+9` test mode |
| label info | `0x2e458` | `+8` tag present, `+0xe` used count, `+0x4e` total count |

Flow on untagged paper (niimblue B1 task: SetDensity, SetLabelType, PrintStart …):

1. PrintStart → print-engine event → `0x10193ac`: state `[0x20614] = 2`, request a tag read
   (`0x1025538` sets bit0 of `[0x205b8+2]`).
2. RFID task `0x10257d4` → `0x10254ea`: three read attempts (`0x1024ed4`) all fail
   (no tag) → `0x102543e`.
3. `0x102543e`: if state == 2 (printing):
   - first failure: `[0x205b8+8] = 1`, one beep, return;
   - the task loop sees `state == 2 && [+8] == 1` and re-requests the read; the
     second failure beeps twice and sets **status bit 19** (`0x10254c2`–`0x10254ca`).
4. The next command (PageStart, status poll …) runs the checker, gets 0x14 and replies
   `0xDB 0x14`; niimblue rejects the whole task.

Outside printing (state != 2) a failed read already returns silently. The print engine
itself treats bit 19 as non-fatal (`0x1015ee4`: bit19 → continue); only the command
handlers refuse.

Nothing in the density / full-quality patches touches this module: the two
`03 21 → 00 21` sites are in handlers of the secondary text protocol (command table
`0x102dcb0`, handlers `0x1022892` and `0x1022ae2`), which niimblue never uses.

## 2. The patch (1 byte)

The error is raised inside `0x102543e` (the RFID read-retry handler). After the retry
feed it sets status bit 19:

```
0x010254c2  movs r1, #1         <-- patch target
0x010254c4  ldr  r0, [r6, #0x14]   ; status word @ 0x20628
0x010254c6  lsls r1, r1, #0x13     ; 1 << 19
0x010254c8  orrs r0, r1
0x010254ca  str  r0, [r6, #0x14]   ; bit 19 set -> checker 0x10108e2 returns 0x14
```

| vaddr | file off | original | patched | meaning |
|---|---|---|---|---|
| `0x010254c2` | `0x154c2` | `01 21` (`movs r1,#1`) | `00 21` (`movs r1,#0`) | `1 << 19` becomes `0 << 19`, so `orrs` writes nothing and bit 19 is never set |

Result: the read-failure path runs exactly as before — including the retry/eject **paper
feed** (`0x1017c04`, ~0x820 steps) that happens on paper insertion — but it no longer
escalates to error `0x14`, so no `0xDB 0x14` / `WriteRfidFail` reaches the host. Successful
reads, the success-beep path (`0x102536e`), tag write-back and the genuine-roll quota logic
(`0x1024f88`, `0x1024e52`, `0x1024ea2`) are untouched, so genuine rolls behave as before.

> **Earlier revision (do not use).** The first bypass changed the state compare at
> `0x01025478` (`cmp r0,#2` → `cmp r0,#0xff`). That compare also gates the feed branch of
> `0x102543e`, so it suppressed the paper-insertion feed entirely — the printer stopped
> feeding on paper change. Zeroing the bit-19 write at `0x010254c2` leaves every feed
> branch intact.

The bypass is part of both builders (`build/build_b1_619.py` rule "RFID read-failure
bypass", `build/build_b1_619_density.py` baseline D) and of the reference rule set
`repro/apply_patch_b1_619.py`; both verifiers check the site
(`verify_b1_619.py` ⑧, `verify_b1_619_density.py` [11]). Every script verifies the
original `01 21` before writing and refuses other firmware versions.

## 4. Label calibration without a tag

Calibration does not depend on the tag, but two different "feeds" are easy to confuse:

- **Retry/eject feed on paper insertion** — this is what `0x102543e` does via `0x1017c04`
  when the tag read fails (the ~15 cm feed seen on paper change). It is *not* gap
  measurement: it feeds a fixed amount and keeps whatever is already out, which is why
  untagged paper "calibrated" wrong. The old `0x01025478` patch removed this feed; the
  `0x010254c2` patch keeps it.
- **Real gap positioning** — command `0x8e` LabelPositioningCalibration → the optical
  state machine `0x1018c5e`, which drives the paper while watching the gap sensor and
  stores the measured pitch in the config (`cfg+0x18/0x1a/0x1c/0x26` by label type).
  Handler `0x101dbf6`: refused (reply 0) while the cover is open, paper is out or a job is
  running; for type 1 it stores `cfg[6]=1`, for 2/5 the matching type, then runs the
  measurement. **No RFID check anywhere in it.** But it only measures a real gap when the
  label type is gap/black-mark — on `continuous` there is no gap to find, so it behaves
  like the fixed feed above.

So without a tag: set the label type first (the tag is the only thing that sets `cfg[6]`
automatically — `0x1024fc2`), then run gap positioning. niimblue sends SetLabelType per
job but has no button for `0x8e`, and `niimblue-node` has no CLI command; the library
exposes `labelPositioningCalibration(type)`. The repo helper sends it over USB:

```sh
python3 src/niimbot_b1.py calibrate --type gap      # or: black, transparent
```

## 5. Status and open items

- Confirmed on hardware (HW 6.01 / FW 6.19): stock 6.19 reproduces the error on untagged
  paper; the first (`0x01025478`) bypass stopped it feeding on paper change; the
  `0x010254c2` bypass restores the feed and still clears the error (to be re-flashed and
  confirmed).
- Gap positioning on untagged paper requires the host to set the label type to gap/
  black-mark first; on `continuous` no gap is measured.
- Status bit 19 can still be set by the write-back / quota paths when a **genuine** tag
  is present and its data is inconsistent (used > total, UID mismatch ×5). That is the
  firmware's intended behaviour and is left alone.
- The read request still happens at every print start (three attempts); this costs a
  few hundred ms but keeps genuine-roll detection working.
