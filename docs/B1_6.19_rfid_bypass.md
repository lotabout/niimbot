# Niimbot B1 firmware 6.19 — RFID read-failure bypass (`WriteRfidFail`, error 0x14)

> Symptom: niimblue aborts every print on untagged / third-party paper with
> `Print error 20: WriteRfidFail`, on **stock** 6.19 as well as on the patched images.
> Reproduced on hardware with stock 6.19 (md5 `fd9efd1441b5f05ca46c310b8d162dc1`).
> Upstream 5.22 never shows this: 5.22 has no error-0x14 path at all.

## 1. Where the error comes from

| Item | 6.19 | Note |
|---|---|---|
| status word | `[0x20614 + 0x14]` = `0x20628` | one bit per printer error |
| status → error code | `0x10108e2` | bit0→1 … bit14→0xF, **bit19→0x14**; 5.22's function stops at bit14 |
| `0xDB` sender | `0x101d4ee` | called from the main loop (`0x1010610`) and the PrintStart (`0x101e010`) / PageStart (`0x101e1f6`) handlers via `0x101d6f0` |
| RFID module | `0x1024c00`–`0x1025b80` | ~3.7 KB **not present in 5.22**; strings `LABEL RFID OK/ERR`, `uuid:` |
| RFID state struct | `0x205b8` | `+2` request bits (bit0 read, bit1/bit6 write-back, bit4 reader enabled), `+8` "first failure seen", `+9` test mode |
| label info | `0x2e458` | `+8` tag present, `+0xe` used count, `+0x4e` total count |

Flow on untagged paper (niimblue B1 task: SetDensity, SetLabelType, PrintStart …):

1. PrintStart → print-engine event → `0x10193ac`: state `[0x20614] = 2`, request a tag read
   (`0x1025538` sets bit0 of `[0x205b8+2]`).
2. RFID task `0x10257d4` → `0x10254ea`: three read attempts (`0x1024ed4`) all fail
   (no tag) → `0x102543e`.
3. `0x102543e`: if state == 2 (printing):
   - first failure: `[0x205b8+8] = 1`, one beep, return;
   - the task loop sees `state == 2 && [+8] == 1` and re-requests the read; the
     second failure beeps twice and sets **status bit 19** (`0x10254c2`–`0x10254ca`).
4. The next command (PageStart, status poll …) runs the checker, gets 0x14 and replies
   `0xDB 0x14`; niimblue rejects the whole task.

Outside printing (state != 2) a failed read already returns silently. The print engine
itself treats bit 19 as non-fatal (`0x1015ee4`: bit19 → continue); only the command
handlers refuse.

Nothing in the density / full-quality patches touches this module: the two
`03 21 → 00 21` sites are in handlers of the secondary text protocol (command table
`0x102dcb0`, handlers `0x1022892` and `0x1022ae2`), which niimblue never uses.

## 2. The patch (1 byte)

| vaddr | file off | original | patched | meaning |
|---|---|---|---|---|
| `0x01025478` | `0x15478` | `02 28` (`cmp r0,#2`) | `ff 28` (`cmp r0,#0xff`) | the "printing" branch of `0x102543e` becomes unreachable |

Result: a failed tag read during printing returns the same way it does when idle: no
beep, no `[+8]` marker, no re-request, no bit 19, no `0xDB 0x14`. Successful reads, the
success-beep path (`0x102536e`), tag write-back and the genuine-roll quota logic
(`0x1024f88`, `0x1024e52`, `0x1024ea2`) are unchanged, so genuine rolls behave as before.

The bypass is part of both builders (`build/build_b1_619.py` rule "RFID read-failure
bypass", `build/build_b1_619_density.py` baseline D) and of the reference rule set
`repro/apply_patch_b1_619.py`; both verifiers check the site
(`verify_b1_619.py` ⑧, `verify_b1_619_density.py` [11]). Every script verifies the
original `02 28` before writing and refuses other firmware versions.

## 4. Label calibration without a tag

Calibration does not depend on the tag. Two paths exist in 6.19:

- **Automatic on paper insertion** (`0x10183f6`): when the paper sensor sees paper again
  the firmware clears the no-paper bit, starts the calibration feed (`0x1018cdc`) and only
  *then* requests a tag read. What the tag adds is the label type: a successful read
  stores `cfg[6]` = type from the tag (`0x1024fc2`). Without a tag the type stays whatever
  the host last sent with SetLabelType (0x23) — so the host must send the right type
  (1 gap / 2 black mark / 3 continuous) before printing, which niimblue does per job.
- **On request**: command `0x8e` LabelPositioningCalibration, payload = label type.
  Handler `0x101dbf6`: refused (reply 0) while the cover is open, paper is out, or a job /
  feed is running; for type 1 it stores `cfg[6] = 1`, for 2 or 5 it stores that type,
  then starts the same calibration feed plus a beep. No RFID check anywhere in it.

niimblue's web UI has no button for `0x8e` and `niimblue-node` has no CLI command, but the
library exposes it (`labelPositioningCalibration(type)`). The repo helper sends it over
USB:

```sh
python3 src/niimbot_b1.py calibrate --type gap      # or: black, transparent
```

## 5. Status and open items

- Confirmed on hardware (HW 6.01 / FW 6.19): stock 6.19 reproduces the error on untagged
  paper; with the bypass the same paper prints through niimblue without `WriteRfidFail`.
- Status bit 19 can still be set by the write-back / quota paths when a **genuine** tag
  is present and its data is inconsistent (used > total, UID mismatch ×5). That is the
  firmware's intended behaviour and is left alone.
- The read request still happens at every print start (three attempts); this costs a
  few hundred ms but keeps genuine-roll detection working.
